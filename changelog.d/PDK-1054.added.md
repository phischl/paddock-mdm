- Upgrade: the upgrade adds two object-store users for organization deletion, with no operator action:
  `./paddock upgrade` generates their four secret files (`.secrets/rustfs_{bundles,escrow}_offboard_{access,secret}_key`)
  and, after `up`, creates the users and their policies with `./paddock bootstrap buckets --add-missing`, which
  changes no existing bucket, policy, user secret or escrowed object; it only removes the obsolete bucket-wide escrow
  read policy `paddock-escrow-read` where an older installation still carries it, and stops when the api lacks its
  narrower `paddock-escrow-api` grant (then run `./paddock bootstrap buckets`). A rollback leaves the two users in place; the
  older release does not use them.
- Organization deletion has its own object-store credentials, held only by the full worker (`paddock-worker`, not the
  ingest workers): they list and delete an organization's objects below `org/` and `apt/` of the bundles bucket and
  every version of its escrowed LUKS header copies and diagnostics bundles, and can read none of them. Without them,
  deleting an organization's objects fails with `object_store_unavailable` while the rest of the worker runs; a version
  kept by Object Lock fails it with `object_retained` instead of counting as deleted. `./paddock check` fails when the
  worker lacks the credentials or another service holds them, and the bucket bootstrap verifies both users.
- The worker's Valkey user may delete, but neither read nor write, bundle pointers (`bp:`) and the time ticket (`tt:`)
  of an organization being deleted (a `DEL`-only ACL selector).
