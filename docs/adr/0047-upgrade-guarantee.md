# 0047 — Upgrade guarantee between consecutive releases
Status: Proposed (architect, 2026-11-04; the maintainer accepts it with the first merged ticket of plan M16)

## Context

Releases 0.1.0-alpha.2 … alpha.6 were upgradeable by the runbook `docs/operations/upgrade.md`
(`./paddock migrate-from`, `pull`, `check`, backup, `up`); alpha.7 moved four stateful images across majors and
declared *no upgrade path*. Nothing in CI installs the previous release and upgrades it; the only test of the
bundle is the smoke test of a fresh installation (`deploy/bundle/ci/smoke.sh`). The roadmap's continuous track
*Upgrade safety* is a Must before beta: a tested upgrade path in CI, pre-upgrade checks in `./paddock`, and a
restore drill. ADR 0013 defines the agent support window in minor versions, which alpha releases do not have
(every alpha is `0.1.0-alpha.N`), and names a "server upgrade tooling" that refuses to strand agents, which does not
exist. ADR 0022 lists "upgrade smoke from the previous release" as a follow-up.

## Options

### From which release the guarantee holds
- **alpha.9 → alpha.10 (first guaranteed pair).** + alpha.9 may still break freely. − The CI test cannot be
  proven before alpha.10; the alpha.9 maintenance bundle (OpenBao 2.7.2, Himmelblau 4.0.8) is exactly the kind of
  change the test is for.
- **alpha.8 → alpha.9 (chosen).** + alpha.8 is released from `main` 80984bde with its bundle and images public on
  GHCR, so the CI job has a real previous release to install; the guarantee is exercised once before it binds.
  − alpha.9 may not bump a stateful image across a major.

### What the test installs
- **The previous release's bundle from GitHub Releases, verified with cosign (chosen).** + The exact artifacts an
  operator has. − Network access to GitHub and GHCR in CI (already the case for the smoke test).
- **A bundle built from the previous tag in the same job.** − Tests the source, not the release.

### How agents stay compatible
- **Keep ADR 0013's minor-version window as written.** − Undefined for alpha versions.
- **Define the window per release until 0.1.0 (chosen):** the server supports agents of its own release and the two
  previous releases; `pkg/bundle` schema versions and `pkg/protocol` stay additive; the upgrade check refuses when
  more than 1 % of active devices run an agent older than that (ADR 0013's rule, now implemented).

## Decision

1. **Guarantee.** From 0.1.0-alpha.8 on, every release N+1 upgrades from release N with `./paddock upgrade` and no
   data loss, and rolls back to N with `./paddock rollback`; CI proves it for every release candidate and for every
   push to `main`. A release that cannot keep the guarantee is not cut; the exception needs an ADR of its own with a
   migration tool shipped in the bundle (the model: a `pg_upgrade` step), never a "fresh installation" note again.
2. **What the guarantee binds.**
   - Database migrations are forward-only and the files of release N are byte-identical in N+1 (`make
     lint-migrations-frozen` compares against the previous tag). `./paddock up` recreates every role after
     `paddock-migrate` completed (Compose dependency order), so a migration may lock tables; it MUST finish within
     the `paddock-migrate` timeout stated in the release notes (default 10 minutes) on the reference database size
     (`docs/operations/capacity.md`).
   - Stateful images (PostgreSQL, Valkey, RabbitMQ, OpenBao, Fleet MySQL, Authentik, RustFS) move within their
     data-compatible line only (patch or minor as the vendor defines compatibility); a major needs its own ADR.
   - The bundle format (`pkg/bundle`), the device protocol (`pkg/protocol`, `api/openapi/device.yaml`), the command
     registry and the event types change additively (ADR 0005, 0013, 0024); the previous release's golden bundles
     and events verify against the new code (`TestPreviousReleaseFixtures`).
   - New `.env` settings have defaults or are listed in the release's `Upgrade:` line; new secrets are generated by
     `./paddock secrets` idempotently; new database roles are created by the migration step from secret files; new
     OpenBao policies and AppRoles are applied by `./paddock upgrade` through the idempotent `openbao-configure.sh`
     when `BAO_TOKEN` is set, and listed as a manual step otherwise.
   - Agents: the server supports agents of its own and the two previous releases. The compiler keeps the renderers
     of those schema versions; older agents receive 426 `agent_unsupported` (ADR 0013). `./paddock upgrade-check`
     refuses when more than 1 % of active devices (or more than 5 devices, whichever is larger) would fall outside
     the window, unless `--allow-unsupported-agents` is given.
3. **Host commands.** `./paddock upgrade-check <old dir>` (read-only; PASS/WARN/FAIL table, `--json`),
   `./paddock upgrade <old dir>` (check, `migrate-from`, `pull`, `check`, `backup now --label pre-upgrade-<N+1>`,
   `up`, post-checks), `./paddock rollback <old dir>` (down; when the release notes say `Schema: migrations …`, a
   restore of the labelled set through `./paddock restore --from local`; `up` in the old directory). The commands
   wrap the runbook's steps and never do anything the runbook does not describe.
4. **Release notes contract.** Every release section of `CHANGELOG.md` has the lines `Schema: …` (exists),
   `Upgrade: from <N>: automatic | steps: <list>` and `Agents: supports <N-2>, <N-1>, <N+1>`; `make release-check`
   refuses a tag without them. `docs/operations/upgrade.md` keeps one subsection per release.
5. **CI.** Job `upgrade` in `ci.yml` (PRs to `main` and `main`) and `release.yml` (after `smoke`): install the
   previous release's bundle on both CI hosts with its agent artifacts, seed an organization, a devicesim device, an
   escrowed secret, a managed file and a notification destination, run `./paddock upgrade-check` and `./paddock
   upgrade` with the candidate bundle, probe the seeded data and a check-in of the previous release's devicesim,
   then the restore drill: `./paddock backup now`, destroy the volumes, `./paddock restore --from` the local target,
   probe again. A failure blocks the release.

## Consequences

- + Operators get one command per direction and a check that tells them before anything changes; CI catches a
  broken migration, a stranded agent or a forgotten secret before the release.
- + No new Go module, npm package or container image.
- − Every release costs the CI job (two installations and a restore, about 25 minutes); every stateful image major
  costs an ADR and a migration tool; the compiler keeps old renderers for two releases.
- − alpha.9 inherits the guarantee from alpha.8: its maintenance bundle is bound by decision 2.
- Follow-ups: ADR 0013 amendment (window per release until 0.1.0); plan M15 provides `./paddock backup now` and
  `./paddock restore`; when 0.1.0 is cut, decision 2's agent window reverts to ADR 0013's minor-version rule.
