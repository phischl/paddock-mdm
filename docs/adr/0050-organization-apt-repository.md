# 0050 — Packages stored in Paddock: a per-organization APT repository (M13c)
Status: Proposed (architect, 2026-11-05; the OpenPGP signing library and the access model are maintainer
decisions marked below — plan M13c plans with the recommendation, "pending")

## Context

ADR 0042 decision 2 (maintainer) said own `.deb` packages come from the customer's own APT repository, added as a
source. Organizations without a repository asked for the obvious: upload a `.deb` to Paddock and assign it. That
makes Paddock a package origin, which is a new trust decision: whoever can publish into that repository ships code
that runs as root on every assigned device, and devices must verify the repository's signature with a key Paddock
holds. Facts: `bundles.<domain>` serves the agent packages publicly (`/packages/*` → RustFS, GET only, no
authentication); `pkg/openpgpkey` reads v4 public keys and computes fingerprints but writes nothing; OpenBao
Transit signs with raw RSA/Ed25519 signatures, not OpenPGP packets; apt verifies `InRelease` with an OpenPGP
signature from the source's `Signed-By` keyring; apt reads credentials from `/etc/apt/auth.conf.d/*.conf`
(0600, root) and follows HTTP redirects.

## Options

### Signing
- **OpenBao Transit raw signature wrapped into an OpenPGP signature packet by own code.** − A hand-written
  OpenPGP *writer* (v4 signature packet, hashed subpackets, EdDSA/RSA MPI encoding) is more surface than the
  reader of M13a; a mistake makes every device trust a malformed anchor. Rejected.
- **A per-organization OpenPGP key generated and used with `github.com/ProtonMail/go-crypto` (BSD-3-Clause), the
  private key encrypted to Transit `software-repo-wrap` and decrypted only in the worker that builds the
  repository (recommended, pending maintainer: new Go dependency).** + Correct packets, maintained library,
  EdDSA keys; the private key never reaches the api or the database in clear. − A new dependency with its own
  supply-chain surface (licence gate: BSD-3).
- **The customer signs offline and uploads signed `Packages`/`Release` files.** − No upload in the portal; a
  manual pipeline on the customer's side; most organizations have none. Not chosen; nothing prevents it later
  through an ordinary `software_source`.

### Access to the repository
- **Public read like the agent packages.** − Organization packages become world-readable by URL. Rejected.
- **HTTP basic authentication with one credential per organization, delivered in every device's signed bundle and
  written to `/etc/apt/auth.conf.d/paddock-repo.conf` (0600) by the software reconciler; the api checks it and
  redirects apt to a presigned object URL (recommended, pending maintainer: a shared secret per organization is a
  public promise about who can read packages).** + apt-native, no client certificates, rotatable in the portal, the
  secret travels only inside authenticated, signed bundles; a device user with root can read it, as they can read
  every file on their device (RR-01). − One credential per organization, not per device; its rotation changes
  every device's bundle.
- **Per-device credentials.** − A row per device and a rotation storm; apt's auth.conf cannot carry a signature.
  Rejected for M13c; possible later.

### Where the files live and who serves them
- **RustFS bucket `paddock-bundles` under `apt/<org_id>/` written by the worker; `bundles.<domain>/apt/*` routed by
  Caddy to the api, which authenticates and redirects to a presigned GET (10 minutes) (chosen).** + The bucket and
  the Caddy site exist; no new container; the api never streams package bytes. − The api gains a basic-auth path
  on the bundles host (rate-limited by ADR 0051's limiter).

## Decision

1. **Repository.** One APT repository per organization at `https://bundles.<domain>/apt/<org_slug>/` with the
   suite `paddock` and the component `main`, architectures `amd64` and `arm64`, flat pool layout
   `pool/main/<p>/<package>/<name>_<version>_<arch>.deb`, `dists/paddock/{InRelease,Release,Release.gpg,main/binary-<arch>/Packages{,.gz}}`.
2. **Uploads.** `POST /api/v1/software-packages` (multipart, ≤ 256 MiB, `org_admin` with step-up, audited
   `software_package.uploaded` with `package`, `version`, `architecture`, `sha256`): the api verifies the `.deb`
   is an `ar` archive with `debian-binary` 2.0 and a `control.tar.*` whose `Package`, `Version`, `Architecture`
   match the request, stores it in the bucket, and queues `software_repo.rebuild`. Deleting a package
   (`software_package.deleted`, step-up) removes it from the pool and rebuilds; a package referenced by a catalog
   entry cannot be deleted (409 `in_use`).
3. **Signing key.** Per organization, EdDSA (Ed25519) OpenPGP key `Paddock <org_slug>` generated by the worker on
   first use, private key Transit-wrapped (`software-repo-wrap`; worker decrypts only), public key and
   fingerprint stored; the repository's `InRelease` is signed at every rebuild; the organization's `software_source`
   of kind `paddock` (system-managed, one per organization, slug `paddock`) carries the public key and
   fingerprint and is rendered like any source (ADR 0042 decision 1). Rotation: `POST
   /api/v1/software-repository/rotate-key` (step-up, audited) generates a new key, re-signs, and the next
   bundles carry the new keyring; the old key is kept for 30 days for reference and then deleted.
4. **Access.** Basic authentication: user `paddock`, password = a 32-byte random secret per organization
   (`software_repo_credential`, Transit-wrapped, rotatable with `POST /api/v1/software-repository/rotate-credential`),
   rendered into the bundle as `software.repository.auth` and written by the agent to
   `/etc/apt/auth.conf.d/paddock-repo.conf` (0600; a protected area). The api answers `GET /apt/<org_slug>/<path>`
   on the bundles host with 401 without the credential, 302 to a presigned GET for a known path, 404 otherwise;
   the limiter of ADR 0051 bounds attempts per IP.
5. **Trust statement.** Uploading a package is root-equivalent on every assigned device: `org_admin` with step-up,
   the SHA-256 in the audit event, RR-114. Paddock scans nothing inside the package (no antivirus, no
   lintian); the maintainer scripts run as root (RR-78 applies).
6. **Fail safe.** A device whose bundle names the Paddock repository but cannot reach it keeps its state; installs
   fail with `source_unreachable` as for any source.

## Consequences

- + Organizations without a repository ship their own packages with the same intents, waves and reports; the key
  never leaves the worker in clear; access is not anonymous.
- − One new Go dependency (pending), one more Transit key, a basic-auth path on the bundles host, and a shared
  per-organization read credential (RR-115).
- Follow-ups: per-device credentials or signed URLs in a later release; the platform-shared catalog (M13c) may
  reference platform-stored packages through the same repository shape under `apt/platform/`.

## Amendment 2026-11-09 (PDK-812) — two Transit keys; signing columns nullable until the first build

Decision 3 has the worker generate the signing key on first use, but the repository row is created earlier by the
api with the access credential (decision 4). The row's signing columns are therefore nullable with a completeness
constraint (all set or all `NULL`); the system `paddock` source exists only once the key does. The credential of
decision 4 is wrapped with its own derived Transit key `software-repo-credential` (api encrypts, compiler
decrypts), not with `software-repo-wrap`, so the compiler — which must decrypt the credential for every bundle —
never gains the ability to decrypt a signing private key; `software-repo-wrap` stays worker-only. Consequence:
two Transit keys instead of one (the "one more Transit key" above becomes two); the policies are per key and
per role, and no role decrypts both. Plan M13c §3.4 decision 11 is edited accordingly (amendment 2026-11-09).
