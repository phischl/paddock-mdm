# Implementierungsplan: M9 — Someone gets told (notifications, findings, audit cursor feed, presence policy)

Status: Ready for implementation · 2026-10-15 · Author: architect
Basis: ADR 0031 (outbound integrations; amends ADR 0010 and ADR 0018), ADR 0018 (lists and dialogs), ADR 0010
(audit pipeline), ADR 0013 (version compatibility), ADR 0006 (OpenBao keys), ADR 0021 (trusted proxies), the

Binding language: **MUST** / **MUST NOT** / **SHOULD** / **MAY**.

## 1. Goal

After M9 a security event reaches a person outside the portal (signed HTTPS webhook, e-mail), the reaction to tamper
events and attention conditions is recorded as findings (acknowledge, assign, close with a reason, every step
audited and visible to auditors), a SIEM or an auditor can pull every audit event exactly once through a
commit-ordered cursor feed, and an organization can declare third-party units whose stop the agent reports as a
tamper event. M12 adds the push forward to SIEMs on the same engine without a new design.

## 3. Binding decisions

### 3.1 Audit index commit sequence (PDK-120)

1. Migration `server/migrations/audit/<next>_commit_seq.sql` (next free goose number at implementation time)
   MUST: `ALTER TABLE audit_event ADD COLUMN commit_seq bigint;` backfill
   `UPDATE audit_event e SET commit_seq = s.rn FROM (SELECT event_id, occurred_at, row_number() OVER (PARTITION BY organization_id ORDER BY recorded_at, event_id) AS rn FROM audit_event) s WHERE e.event_id = s.event_id AND e.occurred_at = s.occurred_at;`
   then `ALTER TABLE audit_event ALTER COLUMN commit_seq SET NOT NULL;`
   `CREATE INDEX audit_event_org_commit_seq_idx ON audit_event (organization_id, commit_seq);`
   `CREATE TABLE audit_org_seq (organization_id uuid PRIMARY KEY, last_seq bigint NOT NULL);`
   `INSERT INTO audit_org_seq SELECT organization_id, max(commit_seq) FROM audit_event GROUP BY organization_id;`
   `ALTER TABLE audit_org_seq ENABLE ROW LEVEL SECURITY; ALTER TABLE audit_org_seq FORCE ROW LEVEL SECURITY;`
   `CREATE POLICY writer ON audit_org_seq TO paddock_audit_writer USING (true) WITH CHECK (true);`
   `GRANT SELECT, INSERT, UPDATE ON audit_org_seq TO paddock_audit_writer;`. No grant to the reader. (A unique
   index on `(organization_id, commit_seq)` is impossible on a table partitioned by `occurred_at`; uniqueness is
   guaranteed by decision 2 and asserted by gate N1.)
2. `auditwriter.Writer.writeGroup` MUST, inside its transaction and before `withoutExisting`: call the new query
   `LockOrgSeq` (`INSERT INTO audit_org_seq (organization_id, last_seq) VALUES (@organization_id, 0) ON CONFLICT (organization_id) DO UPDATE SET last_seq = audit_org_seq.last_seq RETURNING last_seq`),
   assign `commit_seq = last_seq + i + 1` to the fresh events in their `sortEvents` order (`occurred_at`, then
   `event_id`), insert them with `commit_seq`, and after the inserts call `SetOrgSeq(@organization_id, @last_seq)`
   with the last assigned value. An `InsertAuditEvent` that returns no row (a concurrent writer inserted the
   event first) MUST abort the transaction with an error and let the consumer redeliver the batch; it MUST NOT
   skip the event silently any more, because that would leave a gap. The row lock of `audit_org_seq` makes that
   case impossible for writers of the same organization; the error path exists for defence in depth.
3. `auditstore.AuditEvent` gains `CommitSeq int64`; `InsertAuditEvent` gains `@commit_seq`. The `audit verify`
   command (`server/internal/auditwriter/verify.go`) is unchanged: `commit_seq` is index metadata, not part of the
   WORM objects or manifests.
4. Query `ListAuditEventsAfter` (`SELECT * FROM audit_event WHERE commit_seq > @after ORDER BY commit_seq LIMIT @max_rows`,
   RLS supplies the organization) and `LatestCommitSeq` (`SELECT coalesce(max(commit_seq), 0)::bigint FROM audit_event`).
5. `db.AuditReader` gains `InPlatformScope(ctx, fn)`: like `InOrg` but sets `paddock.org_id` to
   `audit.PlatformOrganizationID` explicitly; the only callers are the notifier's platform round (decision 23) and
   the system test fixtures. It MUST NOT be reachable from an HTTP handler (`rlslint_test.go` SHOULD assert that
   no file under `transport/` references it).

### 3.2 Audit cursor feed (PDK-121)

6. `GET /api/v1/audit-events/feed` (operation `feedAuditEvents`, tag `audit`), roles `org_admin`, `org_auditor`,
   sessions and API tokens (`RolesAudit`; an API token with role `org_auditor` or `org_admin` reads it). Parameters
   `after` (integer ≥ 0, default 0) and `limit` (integer 1–1000, default 100). Response 200
   `AuditFeedPage {schema: "paddock.audit.feed.v1", events: [AuditFeedEvent], next_after: integer, latest: integer}`;
   `AuditFeedEvent {commit_seq: integer, event: AuditEvent}` where `event` is the stored event (`event_id`,
   `organization_id`, `occurred_at`, `recorded_at`, `code`, `outcome`, `source`, `actor`, `target`, `params`,
   `error_code`, `correlation_id`) **without** the read-time `device` enrichment of the list endpoint;
   `next_after` is the `commit_seq` of the last returned event (or `after` when empty); `latest` is
   `LatestCommitSeq`. Errors 400 `invalid_request` (`after < 0`, `limit` outside 1–1000), 401, 403. The operation
   carries `x-paddock-feed: { cursor: after, limit: { default: 100, max: 1000 } }` and no `x-paddock-list`.
7. `test/acceptance/list_contract_test.go` MUST exclude operations with `x-paddock-feed` from `collectionGETs`
   (the feed body has `events`, not `items`, so it is excluded by construction; the test MUST additionally assert
   for every operation with `x-paddock-feed` that it declares `after` and `limit`, that its 200 schema has exactly
   the required properties `schema`, `events`, `next_after`, `latest`, and that it has no `x-paddock-list`).
8. The feed reads with `AuditLog.Feed(ctx, after, limit)` through `db.AuditReader.InOrg`; it MUST NOT touch the
   organization pool. The feed is not rendered in the portal.

### 3.4 Destination use cases and API (PDK-123)

14. `server/internal/app/notifications.go`: `type Notifications struct{ runner *ActionRunner; org *db.OrgPool; platform *db.PlatformPool; keys KeyWrapper; audit *db.AuditReader; allowPrivate bool }`
    with `KeyWrapper interface { Encrypt(ctx, key string, plaintext []byte) (string, error) }` (the bao client),
    use cases `List`, `Get`, `Create`, `Update`, `Delete`, `RotateSecret`, `Test`, `ResolvePseudonym`, each in two
    scopes selected by the principal (an organization principal → `ScopeOrg`, a platform principal →
    `ScopePlatform` with `organization_id = audit.PlatformOrganizationID`). Specs: `AllowedRoles: RolesAdmin`
    (organization) / `RolesPlatform` (platform), `RequiresStepUp: true` for `Create`, `Update`, `Delete`,
    `RotateSecret`, `Test`, `ResolvePseudonym`. `List`/`Get`: `RolesAudit` for organizations (auditors see the
    configuration, never secrets), `RolesPlatform` for the platform.
15. `Create` MUST: validate (decision 9, on the plaintext URL), refuse a duplicate name (409 `already_exists`),
    generate the webhook secret, encrypt the secret and the URL (`url_ciphertext`), store `url_display` (scheme,
    host and, when the path is not empty or `/`, `/…`; never the query), insert the destination and its state row with `cursor_commit_seq = LatestCommitSeq` of the
    scope (a new destination never replays history), create the pseudonym key when `pseudonymize_users` and none
    exists, and return the secret **once** in the 201 body (`secret`), never again. Audit params: `name`, `type`,
    `url_display` (webhook), `recipient_count` (email), `filter_mode`, `codes_count`, `pseudonymize_users`,
    `include_params`, `heartbeat_interval_s`, `email_min_interval_s`, `enabled`.
16. `Update` (`PUT …/{id}`) replaces every field except `type` (400 `invalid_request` if changed) and the secret;
    `url` is optional in the body (absent = unchanged; present = validated, re-encrypted, `url_display` updated,
    `changed` lists `url`).
    Enabling a disabled destination MUST take `cursor: "continue" | "skip"` in the body (400 without it):
    `skip` sets `cursor_commit_seq = LatestCommitSeq`. Audit params as `Create` plus `changed` (sorted field
    names) and `cursor`.
17. `RotateSecret` (`POST …/{id}/rotate-secret`) returns the new secret once. `Test` (`POST …/{id}/test`) is
    executed by the notifier, because only the notifier may decrypt the secret: the api inserts a
    `notification_delivery` row of `kind = 'test'` with `delivered_at IS NULL`, answers 202 `{delivery_id}`, and
    the notifier delivers it in its next round (≤ poll interval; webhook: the signed envelope with `events: []`;
    e-mail: one message "Paddock test notification") with exactly one attempt, then sets `delivered_at` or
    `last_error` on the delivery and `last_test_at`, `last_test_ok`, `last_test_error` on the state. The portal
    polls `GET …/{id}` whose `state.last_test` shows the result. The audit event `notification.test_sent` is
    recorded by the notifier with outcome success or failure (params include `requested_by`, the display of the
    administrator stored on the delivery row in `requested_by`).
18. `ResolvePseudonym` (`POST …/{id}/resolve-pseudonym`, body `{pseudonym}`): organization scope only,
    `RolesAdmin`, step-up, audited `notification.pseudonym_resolved` with params `pseudonym` and target
    `{type: organization}`. The api MUST NOT decrypt the pseudonym key, so the lookup is executed by the notifier:
    the api inserts a `notification_pseudonym_lookup` row and answers 202 `{lookup_id}`; the notifier, within one
    round, computes the pseudonym of every `admin_account.username` and every `user.username` of the organization
    with the organization's key and writes `resolved_username` (the match or `''`) and `resolved_at`;
    `GET …/{id}/resolve-pseudonym/{lookup_id}` (`RolesAdmin`, no step-up for the read) returns
    `{pseudonym, username, resolved}` and deletes the row after it was read once; the notifier deletes rows older
    than 10 minutes. The table is part of the migration of decision 10 (§6.2); `notification_delivery` gains
    `requested_by text` for decision 17.
19. API paths (OpenAPI `api/openapi/admin.yaml`, §6.5): organization scope `/api/v1/notification-destinations`
    (list contract, `x-paddock-list`), `/api/v1/notification-destinations/{id}` (GET, PUT, DELETE),
    `…/{id}/rotate-secret`, `…/{id}/test`, `…/{id}/resolve-pseudonym`, `…/{id}/resolve-pseudonym/{lookup_id}`;
    platform scope `/api/platform/v1/notification-destinations` and `…/{id}`, `…/{id}/rotate-secret`,
    `…/{id}/test` (no pseudonym operations: platform events carry no end-user names). Every state-changing
    operation carries `x-paddock-audit` with its code and the `Csrf` parameter; `audit_once_test.go` gets cases
    for each (success, validation failure, wrong role, not found, step-up missing).

### 3.5 Notifier role and webhook delivery (PDK-124)

20. `paddock-server serve notifier` (`server/cmd/paddock-server/notifier.go`) MUST load:
    `PADDOCK_DB_NOTIFIER_URL_FILE`, `PADDOCK_DB_PLATFORM_URL_FILE`, `PADDOCK_AUDIT_DB_READER_URL_FILE`,
    `PADDOCK_OPENBAO_ADDR`, `PADDOCK_OPENBAO_ROLE_ID_FILE`, `PADDOCK_OPENBAO_SECRET_ID_FILE`,
    `PADDOCK_PUBLIC_ADMIN_URL` (for links), `PADDOCK_NOTIFY_POLL_INTERVAL` (duration, default `30s`, minimum `5s`),
    `PADDOCK_NOTIFY_STALL_AFTER` (default `15m`, minimum `1m`), `PADDOCK_NOTIFY_BATCH` (default 100, 1–100),
    `PADDOCK_OUTBOUND_DEV_ALLOW_PRIVATE` (bool, default false; `true` only with `PADDOCK_ENV=development`, else
    `l.Invalid`), the SMTP settings of decision 27, and `PADDOCK_OPS_ADDR`. Readiness: both pools, the reader,
    OpenBao `Ping`.
21. Package `server/internal/notifier` MUST implement the engine: `Run(ctx)` loops every poll interval over every
    organization (`OrgPool.OrganizationIDs`) plus the platform scope; per enabled destination whose
    `next_attempt_at` is not in the future, in order: (a) a pending `kind = 'test'` delivery → deliver, record;
    (b) a `pending_delivery_id` → retry that batch; (c) otherwise scan up to 500 events after `cursor_commit_seq`
    (`ListAuditEventsAfter`), keep the first `PADDOCK_NOTIFY_BATCH` that match the filter, assign `forward_seq`
    (`state.forward_seq + 1 …`), insert `notification_delivery` and `notification_delivery_event` rows, set
    `pending_delivery_id` and advance `cursor_commit_seq` to the last **scanned** event only after the delivery
    succeeded (on failure the cursor stays, the pending delivery is retried; the scan is repeated from the cursor
    on restart and MUST find the same events because the index is immutable); when 500 events were scanned and
    none matched, advance the cursor to the last scanned event without a delivery and continue in the same
    round; (d) heartbeat when `heartbeat_interval_s > 0` and `last_heartbeat_at` and `last_success_at` are both
    older than the interval. Deliveries of one destination are strictly sequential; destinations are independent
    (a stalled one never delays another). At most 20 deliveries per destination and round.
22. Outcome handling per delivery: success → one transaction: `delivered_at`, `attempts`, `cursor_commit_seq`,
    `pending_delivery_id = NULL`, `consecutive_failures = 0`, `first_failure_at = NULL`, `last_success_at`,
    `status = 'active'`, and `ActionRunner.RunTx` recording `notification.delivered` (params `destination`
    (name), `destination_id`, `kind`, `forward_from`, `forward_to`, `count`, `attempts`; target
    `{type: notification_destination, id}`; actor system) — for `kind = 'events'` only; heartbeats and tests are
    not audited as delivered (tests record `notification.test_sent`). If the destination was `stalled`, the same
    action's params carry `resumed: true` and a second action `notification.destination_resumed` (params
    `stalled_for_s`, `forward_from`, `forward_to`) is recorded. Failure → `attempts++`, `consecutive_failures++`,
    `first_failure_at` (if null), `last_error` (error class and HTTP status only: `dns`, `dial`, `tls`,
    `timeout`, `http_<status>`, `redirect`, `denied_address`, `smtp_<code>`), `next_attempt_at = now + min(5s·2^(n−1), 10m)`;
    when `now − first_failure_at ≥ PADDOCK_NOTIFY_STALL_AFTER` and `status = 'active'` → `status = 'stalled'`,
    `stalled_since = now`, one action `notification.destination_stalled` (params `destination`, `destination_id`,
    `since_s`, `last_error`, `forward_seq`).
23. Scopes: organizations run with `worker`-style system principals (`principal.Principal{Kind: KindSystem, Display: "notifier", OrganizationID: org}`)
    through the notifier's `OrgPool` and `AuditReader.InOrg`; the platform scope runs with a system principal

### 3.6 E-mail transport (PDK-125)

27. SMTP is platform configuration of the notifier only: `PADDOCK_SMTP_HOST` (empty = e-mail destinations are
    refused at creation with 409 `email_not_configured` and the portal hides the type), `PADDOCK_SMTP_PORT`
    (default 587), `PADDOCK_SMTP_TLS` (`starttls` default | `implicit` | `none`; `none` only with
    `PADDOCK_ENV=development`), `PADDOCK_SMTP_USERNAME` (optional), `PADDOCK_SMTP_PASSWORD_FILE` (required when a
    username is set), `PADDOCK_SMTP_FROM` (required when the host is set; a valid address),
    `PADDOCK_SMTP_TIMEOUT` (default `30s`). The api learns whether e-mail is configured through
    `GET /api/v1/notification-capabilities` → `{email: bool}` (roles read; the api reads `PADDOCK_SMTP_HOST`
    too, as a non-secret presence flag `PADDOCK_SMTP_ENABLED=true|false` set by compose from the same value).
28. Implementation with the standard library only (`net/smtp`, `crypto/tls`, `net/mail`, `mime`): `implicit` =
    `tls.Dial` then `smtp.NewClient`; `starttls` = `smtp.Dial`, `StartTLS` with `tls.Config{ServerName: host, MinVersion: TLS1.2}`,
    refused if the server does not offer it; `none` = plain. Auth `smtp.PlainAuth` only over TLS (the library
    enforces it) and `smtp.CRAMMD5Auth` as fallback when the server advertises it. One message per batch,
    `text/plain; charset=utf-8`, headers `From`, `To` (every recipient), `Subject`
    (`[Paddock] <organization name or "platform">: <n> security events`), `Date`, `Message-ID`,
    `Auto-Submitted: auto-generated`, `X-Paddock-Delivery`, `X-Paddock-Destination`, `X-Paddock-Forward-Seq: <from>-<to>`.
    Body: one block per event (`occurred_at` RFC 3339, `code`, `outcome`, device hostname or target display,
    `actor.display` (pseudonymized when enabled), link `<PADDOCK_PUBLIC_ADMIN_URL>/devices/<id>/audit` for device
    events, `params` as `key: value` lines only with `include_params`), at most 50 events in detail; above that a
    summary table `code: count` and the line `and N more events; see the portal`. The cursor advances over the
    whole batch (the summary is the delivery). After a success `next_attempt_at = now + email_min_interval_s`
    (digest). No HTML, no attachments.
29. Failure classes `smtp_dial`, `smtp_tls`, `smtp_auth`, `smtp_<code>` (the first 4xx/5xx reply code),
    `smtp_timeout`; the same retry, stall and resume rules as webhooks.

-- name: SetOrgSeq :exec
UPDATE audit_org_seq SET last_seq = @last_seq WHERE organization_id = @organization_id;
-- name: ListAuditEventsAfter :many
SELECT * FROM audit_event WHERE commit_seq > @after ORDER BY commit_seq LIMIT @max_rows;
-- name: LatestCommitSeq :one
SELECT coalesce(max(commit_seq), 0)::bigint FROM audit_event;

## 12. Risks and open points

- **Backfill duration** on a large index: the migration runs in one transaction per goose version; an installation
  with millions of events blocks the writer for minutes. Mitigation: `upgrade.md` states the expected time
  (≈ 1 min per million rows on SSD, to be measured in PDK-120 on the development stack with 1 M synthetic rows
  and recorded in `docs/operations/capacity.md`) and that the writer's queue (no TTL) absorbs the pause.
- **Serialization of writers per organization** on `audit_org_seq`: no measurable change for one-transaction-per-
  organization batches; `PaddockAuditWriterTransactionSlow` watches it.
- **Cursor on a disabled destination**: re-enabling after a long pause with `continue` may send thousands of
  events; the portal asks `continue | skip` and shows the backlog (`latest − cursor_commit_seq`).
- **Attention `since` of `disk_not_compliant` and `agent_outdated` is the last contact** (moves every check-in):
  `opened_at` of such findings is the time the round first saw the condition, not the condition's start; stated
  in the API description; no change to the view in M9.
- **Reason texts may contain personal data** (AUD-06): visible to every organization role in M9 (operators handle
  findings); the portal's reason field carries the hint "facts and ticket references, no personal judgements";
  M10's privacy pack and retention cover the texts. Open question for the orchestrator: restrict `reason` to
  `org_admin` and `org_auditor` (default chosen: visible to all three roles).
- **Webhook URLs with embedded secrets** (Slack-style): decided 2026-10-16 — the URL is encrypted like the HMAC
  secret; administrators see `url_display` only and re-enter the URL to change it; documented in `notifications.md`.
- **host-gateway in CI**: works on Docker ≥ 20.10 Linux; the development stack and the CI runner are Linux. Stop
  condition above if not.
- **E-mail deliverability** is the relay's business (SPF/DKIM of the operator's domain); the notifier only sends
  through the configured relay; documented.
- **Agent rollout halts** (`agent_rollout.halted`) are platform-scope events and reach platform destinations
  only; halted configuration rollouts (`config_rollout.halted`, M11) are organization events and reach the
  organization's destinations. Stated in `notifications.md`.
- **`notification.delivered` volume** with `filter_mode = all`: one event per batch of up to 100 events (≤ 1 %
  of the index); acceptable; stated in the ADR.
