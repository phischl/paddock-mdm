# ISO/IEC 27001:2022 mapping

Where Paddock contributes to Annex A controls, what the evidence is and what remains the operator's duty
(plan M6b decision 5). Paddock is a tool: it supports these controls, it does not implement an ISMS. Risks Paddock
leaves to the operator: [residual-risks.md](residual-risks.md). Audit codes: [audit-codes.md](audit-codes.md).
Data collected from devices: [privacy.md](privacy.md). Licenses: [third-party.md](third-party.md).

## How to read the evidence

- **Audit codes** are stable English identifiers (`device.retired`, `disk.recovery_key_revealed`, …). The audit
  log in the portal (*Audit log*, roles organization administrator and auditor) and `GET /api/v1/audit-events`
  filter by time, code, outcome and actor type. Every privileged action records exactly one event per attempt —
  `success`, `failure` or `denied`; an attempt whose external effect is unknown is finalized as `unknown`
  (`action.finalized_unknown`). Events are stored in English and only displayed in the reader's language.
- **WORM store:** every event is written to an object store bucket with Object Lock in COMPLIANCE mode
  (retention ≥ 400 days, `PADDOCK_AUDIT_RETENTION_DAYS`); no operator credential can delete or shorten it
  (`docs/operations/audit-bucket.md`). `make prod-check HOST=audit ONLINE=1` proves the bucket's lock
  configuration.
- **Hash chain:** per organization and recording day the audit writer seals a manifest with the SHA-256 of every
  object and the hash of the previous manifest, signed with the OpenBao key `audit-chain`.
  `paddock-server audit verify --org <id> --from <day> --to <day>` (in the audit-writer container) checks the chain
  and every object; keep its output with the audit evidence.

## Controls

| Control | Paddock feature | Evidence | Operator duties |
| --- | --- | --- | --- |
| **A.5.33 Protection of records** | Audit events in a separate audit domain (own PostgreSQL index, own host in production), WORM objects with Object Lock COMPLIANCE, signed daily hash chain, retention extendable only; Paddock never deletes audit objects. | Bucket lock configuration (`prod-check ONLINE=1`), `audit verify` output, `docs/operations/audit-bucket.md` | Set the retention to the legal and contractual period, add the lifecycle rule for expiry once it is final, replicate the bucket outside the primary failure domain, protect the audit host, keep the `audit-chain` key and the OpenBao unseal shares under custody. |
| **A.8.15 Logging** | One event per privileged action with actor, step-up flag, target, outcome and parameters (never secrets); device events (tamper, local administrator logins, updates, revocation results) and admin sign-ins (`admin.login`); clients cannot write audit events directly. | `audit-codes.md`, the audit log, `audit verify` | Decide who may read the audit log (role auditor), review it regularly, forward to a SIEM if required, keep host and container logs of the control plane under your own log policy. |
| **A.8.16 Monitoring activities** | Attention list (silent and presumed lost devices, quarantine on suspected clone, non-compliant disk encryption, outdated agents, failed login or sudo configuration, pending or expired revocations); tamper events (`device.tamper_*`); Prometheus alert rules (roles down, dead-letter queues, audit writer lag, OpenBao sealed, OSV data stale, backup age, certificate expiry). | *Attention* page, `device.stale_*`, `device.clone_suspected`, `deploy/compose/prometheus/alerts.yml`, `docs/operations/monitoring.md` | Connect an Alertmanager (not bundled), assign on-call, define reaction times for tamper events and attention entries, document the follow-up of each alert. |
| **A.8.17 Clock synchronization** | All times in UTC; signed device requests must be within ±300 s of server time (else `401 clock_skew` with the server time); audit events carry `occurred_at` and `recorded_at`; the dead man's switch counts uptime since the last signed time ticket, never the device's wall clock. | Gateway refusals, audit event timestamps | Run NTP on every host and device (Ubuntu: `systemd-timesyncd`), monitor host clock drift. |
| **A.8.1 User endpoint devices** | Enrollment with device-bound keys (TPM where present), approval or auto-approval, signed configuration bundles, disk encryption with TPM and boot PIN and escrowed recovery keys and LUKS headers, login assignment and suspension, user lock, Lock and Destroy (flagged), dead man's switch (optional), retire. | `device.enrolled`, `device.approved`, `device.retired`, disk encryption state per device, `revocation.*`, `device.revocation_confirmed` | Define the device policy (who enrolls, which devices are allowed), the lost-device process (Lock, Destroy, two administrators) and the reissue process (retire → Destroy → re-image → enroll). |
| **A.8.2 Privileged access rights** | sudo rights only from permission profiles assigned to users or groups, root-equivalent commands flagged and treated as full rights, generated `sudoers` validated before activation, unexpected `/etc/sudoers.d` files and privileged group members removed and reported; managed local administrator with rotated password, reveal only after step-up, audited; step-up for high-risk portal actions; Destroy needs a second administrator. | `permission_profile.*`, `profile_assignment.*`, `user_group.member_added` (with effective class), `device.tamper_sudo*`, `local_admin.revealed`, `local_admin.login` | Approve profiles with full or root-equivalent rights, review assignments periodically, keep break-glass accounts minimal and sealed, restrict platform administrator and Authentik superuser accounts. |
| **A.8.5 Secure authentication** | Administrators sign in through Authentik (OIDC) with MFA; step-up with fresh MFA for privileged actions; devices authenticate every request with an ECDSA P-256 key and replay protection (nonce, sequence number); device logins through Himmelblau with Hello PIN; user lock blocks online and offline logins. | `admin.login`, step-up flag in audit events, `user.locked`, `device.user_lock_applied` | Enforce MFA in Authentik, set PIN policy (*Login & privileges*), decide the offline login window and how long a lock may take to reach offline devices (residual risks). |
| **A.8.8 Management of technical vulnerabilities** | Inventory and CVE matching through Fleet, severity and fixed version from Ubuntu's OSV data, daily security updates, scheduled regular updates, package holds, install now. | *Vulnerabilities* pages, `device.updates_run`, `package_hold.*`, `platform.osv_stale` | Define patch SLAs per severity, review holds, track devices that need a reboot (Paddock never reboots). |
| **A.8.9 Configuration management** | Declarative, signed and versioned configuration per device (bundles), drift corrected and reported, protected areas re-verified, configuration changes audited. | `device.bundle_applied`, `device.config_drift_corrected`, `managed_file.*`, `managed_unit.*`, `settings.*` | Keep the configuration baseline under change management; review drift and tamper events. |
| **A.8.13 Information backup** | Continuous WAL archiving and daily full backups of both PostgreSQL databases, OpenBao snapshots, Fleet dumps, all encrypted, outside the control-plane host; restore drill with measured RTO. | `paddock_backup_last_success_timestamp_seconds`, backup alert, `make restore-drill` output, `docs/operations/restore.md` | Keep the backup encryption key offline, run and document restore drills, set retention. |
| **A.8.24 Use of cryptography** | Keys by purpose in OpenBao Transit (bundle signing, revocation signing, time tickets, escrow wrapping, audit chain), never in plaintext on application nodes; Ed25519 signed bundles; minisign-signed agent releases verified by the supervisor; keyless cosign signatures and SBOMs for server images; TLS 1.3 externally, TLS between the hosts. | `docs/operations/openbao.md`, `docs/operations/agent-releases.md`, cosign signatures of the release images | Key ceremony and custody (unseal shares, offline release keys with two holders for the revocation key), rotation schedule, certificate management. |
