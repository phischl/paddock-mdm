# ISO/IEC 27001:2022 mapping

Where Paddock contributes to Annex A controls, what the evidence is and what remains the operator's duty
(plan M6b decision 5). Paddock is a tool: it supports these controls, it does not implement an ISMS. Risks Paddock
leaves to the operator: [residual-risks.md](residual-risks.md). Audit codes: [audit-codes.md](audit-codes.md).
Data collected from devices: [privacy.md](privacy.md). Licenses: [third-party.md](third-party.md).

## How to read the evidence

- **Audit codes** are stable English identifiers (`device.retired`, `disk.recovery_key_revealed`, …). The audit
  log in the portal (*Audit log*, roles organization administrator and auditor) and `GET /api/v1/audit-events`
  filter by time, code, outcome and actor type. Every privileged action records exactly one event per attempt —
  `success`, `failure` or `denied`; an attempt whose external effect is unknown is finalized as `unknown`
  (`action.finalized_unknown`). Events are stored in English and only displayed in the reader's language.
- **WORM store:** every event is written to an object store bucket with Object Lock in COMPLIANCE mode
  (retention ≥ 400 days, `PADDOCK_AUDIT_RETENTION_DAYS`); no operator credential can delete or shorten it
  (`docs/operations/audit-bucket.md`). `./paddock check --online` (audit host) proves the bucket's lock
  configuration.
- **Hash chain:** per organization and recording day the audit writer seals a manifest with the SHA-256 of every
  object and the hash of the previous manifest, signed with the OpenBao key `audit-chain`.
  `paddock-server audit verify --org <id> --from <day> --to <day>` (in the audit-writer container) checks the chain
  and every object; keep its output with the audit evidence. The audit writer verifies the chain every night (the
  last seven sealed days and one random older day per organization) and records every run, the CLI's included, as
  `audit.chain_verified` or `audit.chain_verification_failed` in the organization's own audit log
  (`docs/operations/audit-bucket.md` section 3); the result is visible to the auditor role (*Evidence integrity*,
  `GET /api/v1/audit/integrity`).

## Controls

| **A.5.33 Protection of records** | Audit events in a separate audit domain (own PostgreSQL index, own host in production), WORM objects with Object Lock COMPLIANCE, signed daily hash chain, retention extendable only; Paddock never deletes audit objects. | Bucket lock configuration (`prod-check ONLINE=1`), `audit verify` output, `docs/operations/audit-bucket.md`, nightly verification runs and `audit.chain_verified` | Set the retention to the legal and contractual period, add the lifecycle rule for expiry once it is final, replicate the bucket outside the primary failure domain, protect the audit host, keep the `audit-chain` key and the OpenBao unseal shares under custody; the replica is not verified by Paddock (RR-75); set `PADDOCK_AUDIT_INDEX_RETENTION_DAYS` if the index is to outlive the bucket's lifecycle rule. |
| **A.5.28 Collection of evidence** | Signed evidence package per range of sealed days (WORM objects, signed daily manifests, the events, the verification report and runs, the `audit-chain` public keys), built in the audit domain; offline verifier `paddockctl audit verify-export` that needs no Paddock access. | `audit.export_requested`, `audit.export_completed`, `audit.export_downloaded`; the package's `export.json` | Record the `audit-chain` key fingerprint from the *Evidence exports* page in the ISMS and hand it to the auditor out of band; handle packages as confidential (RR-95). | **A.5.34 Privacy and protection of PII** | Negative list of never-collected data ([privacy.md](privacy.md)), retention matrix ([retention.md](retention.md)), purge jobs with deletion evidence, per-organization privacy settings, read-access recording (`audit.searched`, `device.inventory_viewed`), privacy pack. | `retention.md`, `retention.purged`, `device.inventory_purged`, `settings.privacy_changed` | Complete the privacy pack, decide the read-access switches with the works council. |
